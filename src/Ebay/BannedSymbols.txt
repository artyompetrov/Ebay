# DI lifetime bans: one line per overload; the IDs were taken from the package XML docs and cross-checked
# against the overload counts found by reflection.

# Singleton-only DI: every service registered by our code is a stateless singleton. Per-operation state is
# created per call (IDbContextFactory<T>) or passed as a method argument (IWriteModelUnitOfWork).

# EXCEPTIONS (scoped/transient services that exist anyway; none of them is registered through a banned call
# in our code, so no #pragma/[SuppressMessage] is needed or allowed):
# 1. EF Core AddPooledDbContextFactory/AddDbContextFactory also register the context itself as scoped.
#    Only library code consumes it: MassTransit's EF bus outbox resolves the scoped WriteModelDbContext and
#    IPublishEndpoint from the DI scope owned by WriteModelUnitOfWork (the transactional outbox needs both
#    in the same scope), and the ASP.NET Identity / Duende operational stores resolve IdentityDbContext.
# 2. Duende AddOperationalStore calls AddDbContext<IdentityDbContext> internally. Its (no-op) options
#    configuration is re-registered as singleton in AddEfIdentityAdapter; the scoped context it adds is item 1.
# 3. MassTransit: consumers (AddConsumer) are resolved per message in a consume scope, and IPublishEndpoint /
#    ISendEndpointProvider are scoped by design. Consumers only delegate to singleton services.
# 4. ASP.NET Core and ASP.NET Identity/Duende framework services (controllers/Razor Pages, filters,
#    authentication handlers, UserManager/SignInManager, stores, IOptionsSnapshot, ...) are scoped/transient
#    inside the framework; no lifetime option exists for them.
# 5. IHttpClientFactory creates message handlers in its own handler scope (Frontend AddApiAuthorization's
#    BaseAddressAuthorizationMessageHandler and its token provider live there).
# 6. Blazor WebAssembly AddApiAuthorization registers scoped authentication services; the WASM app has a
#    single DI scope for its whole lifetime, so they behave as singletons.
