## Context

See proposal.md - Why. Today two independent caching layers sit in front of the same bytes: an ASP.NET Core `[ResponseCache]` (real server-side output cache, since `UseResponseCaching()` is enabled) at the web-api adapter, and an application-level `IMemoryCache`/`DbCache` pair inside `MeasurementPhotoService`/`MeasurementPlotService`. Neither layer is told about a measurement's status changing; instead, both services re-read `MeasurementState` from the database on every request, before touching their own memory cache, and use that live read to decide whether to return the cached/computed bytes or a sold placeholder. `ProductMeasurement.MeasurementState` is a plain `{ get; set; }` property, so nothing currently observes a status change to raise a domain event from it.

## Goals / Non-Goals

**Goals:**
- Serve photo/thumbnail/plot/tube-description content entirely from the in-process memory cache once resolved, with no per-request database round trip on a cache hit — neither for the sold/not-sold check, nor for the bytes, nor for the matched-pair measurement ids a plot's cache key depends on.
- Make a measurement's sale visible to new requests without waiting for a cache TTL to expire.
- Keep the application layer decoupled from cache internals for the sold/not-sold status specifically: nothing that changes a measurement's `MeasurementState` should call cache-invalidation code directly — that's what the domain event/MassTransit path is for. (`MatchId` invalidation is a deliberate, narrower exception — see Decisions.)

**Non-Goals:**
- Changing `DbCache` (the Postgres-backed, 12-month TTL cache) or `MeasurementPlotWarmupHostedService`. They solve a different problem (avoiding a slow first SVG render right after a deploy, and surviving process restarts) and are explicitly kept as-is, with comments added to document that intent.
- Cross-measurement cache consistency for matched-pair *rendering* (a plot's min/max axes can incorporate a paired measurement's curves, so a paired measurement's own data changing can make this measurement's cached plot visually stale). That coupling already exists independent of this change and is out of scope here. (This is distinct from caching the matched-pair *id list* itself, which this change does address — see Decisions.)
- Guaranteeing sub-millisecond propagation of a status change. See Risks.

## Decisions

**Domain event scope: any status transition, not just "became sold".** Simpler and symmetric: the aggregate doesn't need to special-case which transitions matter to caching; the cache-invalidation consumer is cheap to run and idempotent (worst case, an unnecessary re-resolve on the next request).

**`ProductMeasurement.MeasurementState` becomes a domain method, not a public setter.** A `ChangeState(MeasurementState newState)` method raises the domain event only when the new value actually differs from the current one (no-op assignments raise nothing). This is required groundwork, not incidental cleanup: today nothing observes this property changing, and a public setter can't raise events. `MeasurementService.UpdateMeasurementState` calls this method instead of assigning the property directly.

**Invalidation mechanism: a per-measurement cancellation token, not enumerating cache keys.** Cache keys for plots are composite (`measurementId` + width/height/mergeVertical/etc. + matched-pair ids), and photo keys include both `measurementId` and `photoId` so a cache hit preserves the route's measurement ownership/status semantics. There is still no way to ask `IMemoryCache` to "remove everything for measurement X" by key alone. Instead, a small registry keyed by `measurementId` hands out leased `CancellationTokenSource` generations; every cache entry written for that measurement (photo content, thumbnail, curve plot, tube description) registers that token's `CancellationChangeToken` as an eviction trigger and releases the lease when the cache entry is evicted. The lease is acquired before resolving a cache miss, so an invalidation that happens during slow SVG rendering cancels that in-flight generation and prevents the just-rendered stale value from being stored. The consumer handling the status-changed event cancels (and replaces) that measurement's token, which evicts every existing entry regardless of its key shape, without the invalidation code needing to know what those keys were. Null/unknown measurement requests release their lease immediately because no value is cached, and natural memory-cache eviction releases unused generations.

**Cache the resolved outcome, not just the raw bytes, with a durable bounded fallback.** Currently the sold/not-sold branch is a live check that runs before the cache is even consulted. To stop reading the database on every request, the cache stores the *decision* (serve these real bytes vs. serve the shared sold placeholder) so a cached hit normally never needs to ask the database anything. Because status invalidation is delivered through the outbox/MassTransit path and the legacy write model still saves measurement state and outbox rows through separate DbContexts, memory entries also have a 24 hour absolute expiration in addition to sliding expiration. This bounds stale real bytes even if the invalidation event is lost or delayed, while preserving the value of caching for active listings. The already-existing shared placeholder constants (a single static `byte[]` for photos; a short computed SVG string for plots) continue to be reused by reference/value rather than re-materialized per measurement, so caching the sold outcome for many measurements does not multiply memory use.

**Also cache the matched-pair measurement id list a plot's cache key depends on — closing a gap the review caught.** `MeasurementPlotService.PlotForMeasurementId`/`GetEbayTubeDescription` call `GetMeasurementPairMeasurements` unconditionally, before the cache key is even assembled, so without this the plot endpoints would keep reading the database on every request — cache hit or not — defeating the "no round trip on a hit" goal. This id list is cached per measurementId under the same per-measurement invalidation token as the rest of that measurement's plot/tube-description cache entries, so a cache hit for `/ebay_curves`/`/ebay_tube_description` needs zero database calls.

Caching this list introduces a staleness axis that didn't exist before (previously it was read live on every request, so re-pairing took effect immediately): `MeasurementService.UpdateMeasurementMatchId` must therefore invalidate the changed measurement's own per-measurement token and the tokens for measurements in the old/new matched-pair groups when `MatchId` actually changes (mirroring the no-op guard used for state changes). This invalidation follows the same domain-event/outbox/MassTransit pattern as `MeasurementState`: the aggregate exposes `ChangeMatchId(...)`, raises `MeasurementMatchIdChanged` with old/new normalized match ids only on a real normalized value change, and a consumer/handler invalidates the affected per-measurement cache tokens. This keeps cache invalidation out of the use-case service, preserves cross-process propagation for the cached matched-pair id list, and prevents a peer measurement's already-rendered plot from keeping stale paired axes/list data after re-pairing.

**Verify "no database read" with a query-counting test interceptor, not by inference from response time.** A fast HTTP response doesn't prove no query ran. Since the stack is real Postgres via EF Core with no existing query-counting test infrastructure, the integration tests added for this change register an EF `DbCommandInterceptor` (or equivalent `IInterceptor`) in the test host that counts executed commands, so a test can assert the count is unchanged across a cache-hit request. See tasks.md 4.4/5.4.

**Remove `[ResponseCache]` from the state-dependent endpoints.** With the application layer now serving from memory with event-driven invalidation, the HTTP-level output cache no longer buys meaningful latency (a memory-cache hit is already fast) but remains the only layer that can serve stale pre-sale bytes past a sale — it caches the whole HTTP response ahead of the controller, so a sale during its window doesn't take effect until it expires. Removing it closes that window instead of just bounding it.

**Async delivery via the existing outbox/MassTransit pipeline is an accepted trade-off, not a defect.** The state-changed event travels through the same EF outbox + MassTransit SQL-transport pipeline already used for `MeasurementWatchedOnEbay` and the plot warmup messages, so it is not instantaneous. Existing integration tests already accommodate this kind of eventual consistency with `TestHelpers.RetryUntilValidationSuccessAsync`; the existing sold-placeholder test (currently asserting synchronously right after the status-change call) will move to that same retry-based assertion instead of asserting immediately.

## Risks / Trade-offs

- **[Risk]** A request landing in the gap between the status-change commit and the invalidation consumer running could still be served cached pre-sale bytes. → **Mitigation**: this gap is expected to be short (same infrastructure already relied on elsewhere in this codebase) and is strictly narrower than the fixed 5-minute window the `[ResponseCache]` removal eliminates; it is not unbounded.
- **[Risk]** If the outbox/consumer pipeline stalls (e.g., a backlog or an unhandled exception in the consumer), the cache may keep showing real content until the bounded fallback expires. → **Mitigation**: state-dependent in-memory entries also use a short absolute expiration, so stale real bytes are bounded even when event delivery fails.
- **[Risk]** Caching the resolved sold-placeholder outcome means a measurement that is (re)computed as "sold" stays cached under that decision until the next status change invalidates it, same as the real-content case — no new risk, but worth calling out since it's a change from "always live-checked" to "cached until told otherwise."
- **[Risk]** Caching the matched-pair id list means re-pairing (`UpdateMeasurementMatchId`) on one measurement does not immediately refresh the cached plots of the *other* measurements in its old/new match group. → **Mitigation**: bounded by the existing 6-hour sliding expiration; re-pairing is a rare, staff-only action with no buyer-facing immediacy requirement, unlike a sale.

## Migration Plan

No data migration is needed; this is purely an in-process behavior change riding on already-provisioned outbox/MassTransit infrastructure. Deploy as a single unit (domain method + event + consumer + cache changes + `[ResponseCache]` removal together) — there is no meaningful intermediate state to roll out in phases. Rollback is a plain revert of the deployment.
