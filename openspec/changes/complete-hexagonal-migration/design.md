## Context

See `proposal.md` - Why/What Changes for motivation and scope. Relevant current-state facts that shape the approach:

- `Server.Application/Data/ApplicationDbContext.cs` already carries a self-documenting comment marking itself legacy-only, kept for "compatibility with old code and gradual migration." It is a `DbContext : ApiAuthorizationDbContext<ApplicationUser>, IUnitOfWork` that owns: ASP.NET Identity + Duende IdentityServer operational tables, `Product`, `Lot`, `IgnoredLot`, `Purchase`, `ClientError`, `ProductEmailSendHistory`, `Currency`, `CacheEntry` - plus `ProductMeasurement`, `TubeWorkingPoint`, `MatchedPairDifference`, which are *also* mapped and owned by `WriteModelDbContext` (the target-state write model). These three are transitional: the aggregate types already live in `Server.Domain`, but the legacy context still maps and tracks them for legacy call sites that haven't been moved to the new repositories yet.
- MassTransit's transactional outbox (`x.AddEntityFrameworkOutbox<WriteModelDbContext>(o => { o.UsePostgres(); o.UseBusOutbox(); })` in `Server/Program.cs`) is registered **only** against `WriteModelDbContext`. `UseBusOutbox()` buffers every `IPublishEndpoint.Publish(...)` call in an ambient (async-local) buffer and flushes it when a `SaveChangesAsync` wired to the outbox runs. `ApplicationDbContext.SaveChangesAsync` publishes domain events for its own tracked aggregates, then calls `base.SaveChangesAsync()`, then explicitly calls `_writeModelUnitOfWork.SaveChangesAsync(...)` (i.e. `WriteModelDbContext.SaveChangesAsync`) - that second call is what actually flushes the buffered outbox messages. This means legacy-tracked domain events are only reliably published because `ApplicationDbContext` happens to always cascade into a `WriteModelDbContext` save; there is no true cross-context atomicity (if the legacy save succeeds and the cascaded write-model save fails, buffered events are lost). This is an existing, accepted quirk - not something this change fixes ad hoc; it disappears naturally once `ApplicationDbContext` is retired and everything commits through `WriteModelDbContext` alone.
- `Server.Application.New`/`Server.Domain` already fully implement the target pattern for `LotForSale`, `ProductMeasurement`, `MeasurementPhoto`, `MatchedPairDifference`, `TubeWorkingPoint`, `Product` (partially - see below), so those slices are the reference implementation, not migration targets themselves - except for finishing the legacy `ApplicationDbContext` mappings that still shadow them.
- **Corrected finding (from subagent review of this design):** `WriteModelDbContext` (`Server.Adapters.Driven.EF.WriteModel/WriteModelDbContext.cs`) has exactly two `DbSet`s: `LotForSales` and `MeasurementPhotos`. `Product`, `TubeWorkingPoint`, `MatchedPairDifference`, and `ProductMeasurement` have repository *interfaces* in the target shape (`IProductRepository`, `ITubeWorkingPointsRepository`, `IMatchedPairDifferenceRepository`, `IMeasurementRepository`), but their repository *implementations* (`ProductRepository`, `TubeWorkingPointsRepository`, `MatchedPairDifferenceRepository`, `MeasurementRepository`, all in `Server.Adapters.Driven.EF.WriteModel/Repositories`) take `ApplicationDbContext` in their constructor, not `WriteModelDbContext`. So these four aggregates are **not** already decommissioned from the legacy context - each module's migration phase (sections 3 and 4 of `tasks.md`) must itself add the EF mapping/migration to `WriteModelDbContext` and repoint the repository implementation, not just redirect application-layer call sites to "the existing repository." Only `LotForSale` and `MeasurementPhoto` are genuinely done end-to-end.
- `ApplicationDbContext` also owns `ProductPassport` (`DbSet<ProductPassport> ProductPassports`), used by `ProductPassportFileController` and `EbayControllerImplementation` - omitted from an earlier draft of this design and from the table list in `proposal.md`'s Impact section; it is now included in section 6/7 of `tasks.md`.
- `Server.Domain/Lot.cs` (an eBay listing: price, shipping, condition, currency, a `Purchases` navigation) is a **different, unrelated domain concept** from `Server.Domain/LotForSale/LotForSale.cs` (the migrated aggregate: name, product id, product/measurement state). The similar name is coincidental. `Lot` carries real behavior (price/metric calculation, cross-entity `Purchases` navigation) and has no aggregate design yet - it cannot be moved to `WriteModelDbContext` as a mechanical schema copy the way `CacheEntry`/`ClientError` can; it needs the same kind of domain-design step as `Product`'s pricing logic (task 4.1), including resolving its `Purchases` navigation against the DDD rule in `AGENTS.md` forbidding cross-aggregate navigation properties (reference by `AggregateId` instead).
- `TransactionScopeFactory` (`Server.Application/Infrastructure`) exists specifically to wrap call sites that must atomically touch both the legacy context and the write model under an ambient `TransactionScope`, papering over the lack of a single unit of work. It has exactly 5 real call sites: `EbayControllerImplementation.cs` (x3), `SaleAdvertisementCleanupBackgroundTask.cs`, `ChipfindBackgroundTask.cs`, and `CalculatePricesForLotConsumer.cs` - a reliable, non-trivial map of every place where legacy and new state are still coupled in one business operation, landing in phases 4-6 below.
- `Server.Application` also has several small files with no natural single-module home: `Infrastructure/BackgroundTask.cs` (the shared abstract base every `HostedServices/*` class derives from), `WellKnown.cs` (constants used across pricing, ChipFind/Currency/SaleAdvertisement timing, and GeoIp), `ServiceCollectionExtensions.cs` (legacy composition-root DI wiring called from `Program.cs`), `DatabaseConcurrentAccessSemaphore.cs`, `EbayServerOptions.cs`, `ImageCacheOptions.cs`. These are assigned to specific phases in `tasks.md` rather than left implicit.
- `Server.Adapters.Driving.MassTransit`'s existing, already-migrated `MatchedPairsCalculatorConsumer` currently has a compile-time dependency on the legacy assembly: it references the `CalculateMatchedPair` message record defined in `Server.Application/Consumers/MatchedPairs/CalculateMatchedPair.cs` (`Server.Application/Services/Measurement/MatchedMeasurementService.cs` also references it). This is evidence that "already migrated" pieces can still carry a hidden legacy reference; the final deletion of `Server.Application` (section 7) must be preceded by a solution-wide grep for `using Server.Application.` in every `Server.Adapters.*`/`Server.Application.New` project, not assumed clean because a module was marked done earlier.

## Goals / Non-Goals

**Goals:**
- Define a per-module migration recipe that is mechanical enough to repeat ~15 times without re-deriving the approach each time.
- Sequence the modules so each phase is independently shippable, leaves the app fully working, and never leaves a module "half migrated" across a merge.
- Front-load the highest-uncertainty/highest-blast-radius piece (Identity + `ApplicationDbContext` retirement) only after every safer module is done and the team has repeated the recipe enough times to trust it.
- Preserve every existing external contract (HTTP routes/DTOs, message contracts, DB data) unless a task explicitly says otherwise.

**Non-Goals:**
- Changing any user-observable behavior, HTTP contract, or message contract as a side effect of moving code (call out and fix separately if found).
- Solving the outbox/atomicity quirk described above as a targeted fix - it is resolved as a natural consequence of retiring `ApplicationDbContext` in the last phase, not patched earlier.
- Re-litigating the target pattern itself - it's already built and documented in `src/Ebay/AGENTS.md`; this change only applies it.
- Adding new product features or new `openspec/specs/**` capabilities (see `skip_specs: true`).

## Decisions

### One phase = one bounded module, old code deleted in the same phase
Each `tasks.md` phase picks one legacy module (a `Consumers/*` group, a `HostedServices/*` item, a `Services/*` item, a `Controllers/*` item, or a `Data`/`Infrastructure` cluster) and, within that phase: extracts domain logic into `Server.Domain` (only if the module has real domain rules - some are pure I/O adapters with no domain logic), adds ports (`Server.Application.Abstractions.Driven`/`.Driving`) if needed, adds a use-case service in `Server.Application.New`, adds/extends the adapter in the matching `Server.Adapters.*` project, rewires DI/`Program.cs`, and **deletes the legacy files**. Rejected alternative: migrate all "domain extraction" first across every module, then all "ports," etc., in horizontal layers - rejected because it leaves the app in a broken intermediate state for the whole migration and makes each PR much larger to review with no working checkpoint.

### Sequencing: lowest-coupling modules first, `ApplicationDbContext` retirement last - but each table moves with the phase that needs it
Order (revised after review - the original draft wrongly deferred every table move to a final "retirement" phase, which doesn't work because phases 4 and 6 directly query tables that would still only exist on the legacy context; each phase now migrates the specific tables its own call sites touch):
1. Pure-logic `Infrastructure/*` helpers with no DB/Identity coupling - relocate each to whichever layer actually owns its one caller; leave `TransactionScopeFactory` in place (its call sites are the coupling map for phases 4-6, see Context), and leave `BackgroundTask.cs`/`WellKnown.cs`/`ServiceCollectionExtensions.cs`/the small options types for the phases that actually consume them.
2. `Services/LotDataExtractor/*` and `Services/GeoIp/*` - self-contained, no domain aggregate or table involvement, easy first real modules to prove the recipe.
3. `Services/Measurement/MatchedMeasurementService`, `Services/MeasurementPlot/*`, `Services/MeasurementWatching/*`, `TubeWorkingPointService` - these touch `ProductMeasurement`/`TubeWorkingPoint`/`MatchedPairDifference`, which have target-shape repository *interfaces* but implementations still on `ApplicationDbContext` (see Context). This phase must itself add the `WriteModelDbContext` mapping/migration for these three and repoint `MeasurementRepository`/`TubeWorkingPointsRepository`/`MatchedPairDifferenceRepository`, not just redirect call sites to "the existing repository."
4. `Consumers/PriceCalculator/*`, `Consumers/EbayCurvesCacheWarmUp/*`, `Consumers/MatchedPairs/CalculateMatchedPair.cs` - `CalculatePricesForLotConsumer` reads `Currencies`, `Lots` (with a `Purchases` include), and `Products` directly from `ApplicationDbContext`, so this phase must add `Product`'s `WriteModelDbContext` mapping (repointing `ProductRepository`) and do real domain design for `Lot`/`Purchase`/`Currency` (see Context's `Lot` vs `LotForSale` note) - it cannot be scoped as "just redirect to `IProductRepository`."
5. `HostedServices/*` (ChipFind, Currencies, DbCache cleanup, SaleAdvertisements) - each becomes a hosted service registered from its owning adapter (e.g. ChipFind's own adapter project already exists: `Server.Adapters.Driven.ChipFind`) instead of `Server.Application`; `CacheEntry` (the storage behind `DbCache`) and `BackgroundTask.cs` (the shared hosted-service base class) move here.
6. `Controllers/*` → `Server.Adapters.Driving.WebApi`, per the `web-api` skill's conventions. `EbayControllerImplementation` and `ProductPassportFileController` are the last call sites touching `IgnoredLot`, `ClientError`, `ProductEmailSendHistory`, and `ProductPassport` directly - this phase adds their `WriteModelDbContext`/read-model mappings.
7. `ApplicationDbContext` retirement: by this point every domain/write table has already moved in the phase that owned it (3-6); this phase covers only what's left - migrate ASP.NET Identity + Duende IdentityServer operational tables onto their own dedicated `DbContext` (not folded into `WriteModelDbContext`, to keep write-model aggregates and auth infrastructure separate), do a solution-wide grep for any remaining `using Server.Application.` reference (see Context) and clear it, remove `TransactionScopeFactory` (its 5 call sites should now all commit through a single `WriteModelDbContext` save), then delete `ApplicationDbContext`, `Server.Application/Migrations`, `WellKnown.cs`/`ServiceCollectionExtensions.cs`/the remaining options types, and finally the empty `Server.Application` project itself.
Rejected alternative: retire `ApplicationDbContext` first to "unblock everything at once" - rejected because it is the single highest-risk, highest-blast-radius piece (touches auth), and doing it first means the very first phase has no working recipe to fall back on and no safety net if something goes wrong. Rejected alternative (from the original draft): defer *every* table move to this final phase - rejected per the review finding above, since phases 4 and 6 cannot be correctly scoped without their tables already moved.

### Schema moves are stop-the-world EF migrations, not dual-write, done inside the owning phase
For each table moving from the legacy schema to `wm` (or a read-model equivalent): the phase that migrates the table's owning module adds the new table via an EF migration on the owning adapter project, copies existing rows in the same migration (SQL `INSERT ... SELECT` from old table to new), cuts application code over to the new context, and a later migration drops the old table once the cutover is verified in production. A table with real behavior (`Lot`, `Product`) gets a domain-design step first (see `Lot` vs `LotForSale` in Context); a table with no behavior (`CacheEntry`, `ClientError`, `ProductEmailSendHistory`, `IgnoredLot`, `Currency`) is a mechanical copy. Rejected alternative: a dual-write/blue-green window reading and writing both tables - rejected as unnecessary complexity for a single-writer internal application with a maintenance-window deploy model already used for migrations elsewhere in the repo (see `AGENTS.md` DB migrations section); the simpler approach matches existing project conventions and this app's scale.

### Identity/IdentityServer gets its own `DbContext`, not `WriteModelDbContext`
`ApplicationUser` and the Duende `OperationalStoreOptions` tables are authentication infrastructure, not a write-model aggregate; folding them into `WriteModelDbContext` would make an unrelated concern (auth) a dependency of every write-model migration. They move to a small dedicated `Server.Adapters.Driven.EF.Identity` (name TBD in tasks) context/migrations project instead, registered independently in `Program.cs`.

### One `tasks.md`, not one OpenSpec change per module
Given every phase shares the same recipe and sequencing rationale above, tracking it as a single change with a long, numbered `tasks.md` (matching the project's existing convention, e.g. `2026-09-13-complete-scenario-test-coverage`) lets one `openspec-apply-change` pass and one running task list carry the whole effort across many sessions/PRs, instead of re-deriving proposal/design for ~15 near-identical smaller changes. Each phase's tasks still land as its own PR(s); this is a project-management decision about the OpenSpec change boundary, not about PR size.

## Risks / Trade-offs

- [Moving `ProductMeasurement`/`TubeWorkingPoint`/`MatchedPairDifference` off the legacy mapping could silently change EF query behavior for any remaining legacy call site that queries them via `ApplicationDbContext` directly] → grep every legacy read of these DbSets before removing the mapping in phase 3/7; route reads through the existing `Server.Application.Abstractions.Driven.Abstractions.Queries.I*Queries` ports instead.
- [The outbox-flush-via-cascade quirk (see Context) means a phase's domain events only flush reliably once that aggregate's repository implementation itself moves off `ApplicationDbContext` onto `WriteModelDbContext` - **not** merely by redirecting an application-layer call site to "the existing repository," since the repository itself is still `ApplicationDbContext`-backed for `Product`/`ProductMeasurement`/`TubeWorkingPoint`/`MatchedPairDifference` today] → each phase that migrates one of these repositories (3, 4) must include the `WriteModelDbContext` mapping/migration as part of the same phase, and verify with an explicit integration test that the aggregate's domain events still flush after the move, before considering the phase done.
- [`TransactionScopeFactory` call sites mark real cross-context atomicity needs; removing a call site's `ApplicationDbContext` dependency without checking whether it was inside a `TransactionScope` together with a write-model call could silently drop atomicity] → audit every `TransactionScopeFactory` usage in the phase that touches its call site (4, 5, 6 - see Context for the exact site-to-phase mapping), confirm both sides of that call now commit through a single `WriteModelDbContext` save, and only then remove that specific `TransactionScope` usage; delete the factory itself in phase 7 once all 5 sites are cleared.
- [A stop-the-world schema-move migration (Decision above) requires a deploy window; doing this for `Product`/`Lot`/`Purchase` etc. touches heavily-referenced tables] → schedule these specific migrations deliberately (not silently inside an unrelated feature PR) and verify row counts match between old and new tables before dropping the old one.
- [Identity/IdentityServer migration (phase 7) is the highest-risk single step - a mistake locks out all users] → do it last, in its own PR, with a tested rollback (keep the old `ApplicationDbContext`-backed tables until the new context is verified in production for a full auth cycle - login, token refresh, logout).
- [Large multi-session effort risks drifting from the recipe/order above as it's implemented over many sessions] → `tasks.md` phases are self-contained and checkable independently; re-read `design.md`'s Decisions before starting any phase not done in the same session it was planned.
- [`MatchedPairsCalculatorConsumer`, an already-migrated adapter, still compiles against the legacy `CalculateMatchedPair` message record - a sign that "migrated" modules can carry a hidden legacy reference that only surfaces when `Server.Application` is finally deleted] → phase 4 relocates the `CalculateMatchedPair` message contract (not just deletes it) and updates the consumer's reference; phase 7 does a solution-wide `using Server.Application.` grep before the final project deletion rather than trusting each phase's own "no remaining references" check in isolation.
- [`Product.ProductCalculationResult` currently has a public setter, which already violates `AGENTS.md`'s own "no public setter for behavior-bearing state" rule, independent of this migration] → phase 4's domain-design step for `Product`'s pricing logic (task 4.1) fixes this alongside adding the new pricing methods, rather than leaving the pre-existing violation in place next to newly-added domain methods.
- [Flagged by GitHub PR review: deleting `Server.Application/Migrations` (task 7 cleanup) removes the only migration history that creates the legacy `ProductMeasurements` table, but the already-applied write-model migration `20260222182724_BackfillLotForSaleFromMeasurements` reads that table directly via raw SQL (`FROM "ProductMeasurements" pm` / `UPDATE "ProductMeasurements" pm`). A fresh/empty database bootstrap - including `Tests.Integration/IntegrationTestsSetupFixture`, which creates a brand-new randomly-named database per test run - would fail with "relation does not exist" the moment that migration replays, even though it's a harmless no-op in every real environment (already applied there, so it never re-runs)] → before deleting `Server.Application/Migrations`, guard `BackfillLotForSaleFromMeasurements`'s SQL bodies with an `IF EXISTS (SELECT 1 FROM information_schema.tables WHERE table_name = 'ProductMeasurements')` check (or equivalent) so it degrades to a no-op against a database that never had the legacy table. Editing an already-applied historical migration's `Up()` is safe here specifically because it only changes behavior for environments where it hasn't run yet (EF tracks applied migrations by name in `__EFMigrationsHistory`, not by re-checksumming the file) - confirmed no other write-model migration references a non-`wm`-schema table this way (grepped the full migration history). Verify by running the full integration test suite (which bootstraps a fresh database) after `Server.Application/Migrations` is deleted.
