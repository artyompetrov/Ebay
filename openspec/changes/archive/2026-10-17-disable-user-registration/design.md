# Design

## Context

- Identity is wired in `Server.Adapters.Driven.EF.Identity` (`AddEfIdentityAdapter`): `AddDefaultIdentity<ApplicationUser>` brings in the ASP.NET Core Identity UI (`Microsoft.AspNetCore.Identity.UI` 10.0.0, Bootstrap 5 pages), and Duende IdentityServer (via `AddApiAuthorization`) uses its `Account/Login` page for the `Frontend` and Chrome extension clients.
- `Server/Program.cs` maps `MapRazorPages()`, `MapControllers()` and, last, `MapFallbackToFile("index.html")`. The fallback matches any path without a file extension and any HTTP method. So once a page route is removed, a request to its path would get the Blazor `index.html` with `200 OK`, not `404`.
- The only project-owned Identity UI file is `Server/Areas/Identity/Pages/Shared/_LoginPartial.cshtml`; every other Identity page comes from the package.
- No external login providers are configured, so `Account/ExternalLogin` cannot create accounts.
- Integration tests run the real host through `WebApplicationFactory<Server.Program>` against a real PostgreSQL (`Tests.Integration`); frontend components are tested with bUnit (`Tests.Frontend`).

## Goals / Non-Goals

**Goals:**
- Make the handlers of the registration-related pages unreachable, not just hidden.
- Keep the list of disabled pages in one place, inside the Identity adapter.
- Change the sign-in page only in its markup; keep its sign-in logic identical to the framework's.

**Non-Goals:**
- An authorization policy or allowlist for existing accounts.
- Replacing the email-confirmation flow with a real Identity email sender.

## Decisions

### D1. Remove the page routes with a Razor Pages route-model convention
`AddEfIdentityAdapter` registers, for each disabled page (`/Account/Register`, `/Account/RegisterConfirmation`, `/Account/ConfirmEmail`, `/Account/ResendEmailConfirmation` in the `Identity` area), an area page route-model convention that clears the page's selectors. A page without selectors gets no endpoint, so its handlers (including `UserManager.CreateAsync` in `Register`) can never run, whatever the request.

Alternatives considered:
- *Scaffold the pages as stubs returning `NotFound()`*: four extra pages whose routes still exist and could be "fixed back" by a later scaffold; more code for the same effect.
- *Block the paths in nginx*: depends on the deployment, not covered by the application's tests, and does not protect local or alternative hosting.
- *Middleware matching the request path*: string matching on paths duplicates routing and is easy to bypass with path variants (case, trailing slash, encoded characters).
- *Switch to `AddIdentityCore` without the UI*: also removes `Login`, which IdentityServer needs.

### D2. Answer the removed paths with an explicit 404
Because of the SPA fallback (see Context), D1 alone would make these paths return `index.html` with `200 OK`. The Identity adapter therefore also maps the same paths, for all HTTP methods, to an endpoint that returns `404 Not Found`. These endpoints have higher priority than the fallback. With the page routes removed by D1 they don't conflict with Razor Pages. Both D1 and D2 are driven by the same list of page names, so adding or removing a page changes one place. The mapping is exposed as an adapter extension called from `Program.cs` next to the existing `UseEfIdentityAdapterAuthentication`, consistent with how the adapter already plugs into the pipeline.

Alternative considered: leave the fallback answering. That still creates no accounts, but it contradicts the spec's `404` and makes the endpoints look alive to scanners. Rejected.

### D3. Own the `Login` page by scaffolding it from Identity UI 10.0.0
Add `Server/Areas/Identity/Pages/Account/Login.cshtml` and `Login.cshtml.cs`, generated by the Identity scaffolder (or ported 1:1 from the scaffolder output of the same package version) for `ApplicationUser`. The page lives next to the existing `_LoginPartial.cshtml` in `Server`. The only change from the generated code is removing the "Register as a new user" and "Resend email confirmation" links. Sign-in logic (lockout, two-factor redirect, `returnUrl` handling, external-login section) stays as generated. Its `.cs` file follows the project C# style rules.

Alternatives considered:
- *Override only `Login.cshtml` and keep the package's page model*: the package binds the generic internal `LoginModel<TUser>` through its own infrastructure, so overriding the view alone is not reliably supported.
- *Hide the links with CSS or rewrite the HTML response*: the links stay in the markup; a workaround, not a fix.

### D4. Remove the remaining links in place
- Delete the `Register` anchor from `Frontend/Shared/LoginDisplay.razor`.
- Delete the `Register` list item from `Server/Areas/Identity/Pages/Shared/_LoginPartial.cshtml`.

The Blazor `authentication/register` action of `RemoteAuthenticatorView` stays routable (it is part of the generic `authentication/{action}` page), but nothing links to it any more, and following it ends at the `404` from D2.

### D5. Tests
- `Tests.Integration`: HTTP tests through `IntegrationTestsSetupFixture.Factory` with redirects disabled:
  - each disabled page returns `404` for `GET` and `POST`;
  - a `POST` to `Register` creates no user (checked through `UserManager`);
  - the `Login` page returns `200` and has no links to `Register` or `ResendEmailConfirmation`;
  - sign-in through the `Login` form succeeds for an existing user and fails for a wrong password. The test creates the user through `UserManager` and takes the antiforgery token from the rendered form.
- `Tests.Frontend`: a bUnit test of `LoginDisplay` for an anonymous user: there is a "Log in" link and no "Register" link.
- Every test is tagged with `[OpenSpecScenario("user-accounts", ...)]`.

## Risks / Trade-offs

- [Updating Identity UI won't update the scaffolded `Login`] → It must be re-scaffolded when the package's major version changes. The sign-in tests (D5) catch behavioral breakage.
- [An overridden page may not pick up the package's `_ViewStart`/`_ViewImports`, and the page renders without the Identity layout or tag helpers] → Add the scaffolder's `_ViewImports.cshtml`/`_ViewStart.cshtml` under `Areas/Identity/Pages` if needed. The `Login` page test asserts a working form (antiforgery token present).
- [The fallback assumption in D2 is wrong and the paths already return 404 without the explicit endpoints] → The D2 endpoints are then redundant but harmless; the 404 tests hold either way. During implementation, check whether they are needed and drop them if not.
- [A future scaffold re-adds `Register` and silently restores the route] → The 404 tests and the spec coverage check fail in CI.

## Migration Plan

Deploy as usual; no data or configuration changes. Existing accounts and sessions are unaffected. Rollback is a revert of the change. After deployment, check that `POST https://<domain>/Identity/Account/Register` returns `404`.
