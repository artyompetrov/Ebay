## Context

See proposal.md - Why. Concretely, `EbayControllerImplementation` (724 lines) mixes two shapes today:

- **Already correct**: `GetTubeWorkingPointAsync`/`UpsertTubeWorkingPointAsync` (`_tubeWorkingPointService`), `FindMatchedMeasurementsAsync` (`_matchedMeasurementService`), the `GetAllProductsAsync`/`CreateProductAsync`/... product methods (`_productService`), and every `Measurement*` method (`_measurementService`) - the controller calls one service method and maps the result, nothing else.
- **Still wrong**: `UploadProductPassportAsync`/`DeleteProductPassportAsync`/`UpdateProductPassportAsync` (passport CRUD + order-shifting math, direct `IProductPassportRepository` + `IWriteModelUnitOfWork`), `UpsertLotInfoAsync`/`DeleteLotInfoAsync` (`Lot` aggregate lifecycle, purchase-history sync, un-ignoring, `IPublishEndpoint.Publish`, `ILotRepository`, `IWriteModelUnitOfWork`, `BeginTransactionAsync`), `IgnoreLotsAsync` (`IIgnoredLotRepository` + `IWriteModelUnitOfWork`), `SaveErrorAsync` (`IClientErrorRepository` + `IWriteModelUnitOfWork`), `CalculatePricesForProductAsync`/`CalculatePricesForAllAsync` (`IPublishEndpoint.Publish` + `IWriteModelUnitOfWork` directly).
- **Already correct but easy to miss**: `GetCurrenciesAsync` (`ICurrencyQueries`) and `GetSaleAdvertisementsAsync` (`IProductEmailSendHistoryQueries`) are pure reads through query ports already - there is no Currency or SaleAdvertisement *write* path anywhere in this controller, so despite being named in the original review discussion, neither needs a new use-case service. Query-port reads called directly from the controller (`_lotQueries`, `_ignoredLotQueries`, `_passportQueries`, `_currencyQueries`, `_productEmailSendHistoryQueries`) are the established, unflagged pattern in this codebase and stay as-is; only the *write*/command paths and the one MassTransit publish-only trigger paths are in scope.

`IWriteModelUnitOfWork`/`IUnitOfWorkTransaction` and the repository ports already exist and don't change shape - the same `LotRepository`/`IProductPassportRepository`/etc. used today keep being used, just from a new service instead of from the controller.

## Goals / Non-Goals

**Goals:**
- `EbayControllerImplementation` ends with zero direct dependencies on repositories, `IWriteModelUnitOfWork`, or `IPublishEndpoint`/MassTransit - only application-layer services, query ports, and HTTP<->DTO mapping (including the manual constraint validation the web-api skill already scopes to the adapter, e.g. `UpsertLotInfoAsync`'s "Shipping/ShippingAdditional required" / "all categories set" checks - those stay in the controller, they're exactly what that skill reserves for the adapter).
- `Server.Adapters.Driving.WebApi.csproj` has no direct `MassTransit` `PackageReference` once nothing in that project calls `IPublishEndpoint` directly.
- One OpenAPI contract (`Server.Contracts/WebApi/WebApi.yaml`), one NSwag generation style, one generated controller base class for every endpoint this project serves.
- No change to any endpoint's externally observed behavior: same paths, methods, request/response shapes, status codes. `Tests.Integration`'s existing flow tests (`LotPricingFlowTests`, `IgnoredLotFlowTests`, others) are the proof of that and must keep passing unchanged throughout.

**Non-Goals:**
- Not touching the already-correct methods (`_measurementService`/`_matchedMeasurementService`/`_tubeWorkingPointService`/`_productService`-backed) beyond whatever the contract merge's generation-style change mechanically requires of every method in the file.
- Not adding new use-case services for Currency or SaleAdvertisement reads - they're already correctly shaped.
- Not changing the actual price-calculation/recalculation business logic (`CalculatePricesForLotConsumer` etc.) - only how the *trigger* is published.
- Not revisiting `DeleteLotInfoAsync`'s just-added explicit transaction (from the PR #355 review-fix round) beyond moving it into the new `LotService` verbatim.

## Decisions

**One OpenSpec change covering both the service extraction and the contract merge, done in that order.** The contract merge changes every legacy endpoint's generated method signature (from a concrete `Controller`-base-class method throwing `NonOkHttpAnswerException` to an abstract-base-class method returning `ActionResult<T>`), so touching business logic *and* the generation style in the same edit per method would make each step hard to verify independently. Extracting the services first (same generation style, same error-throwing convention, only the logic moves) keeps each intermediate commit verifiable against the unchanged HTTP contract; the contract/style merge afterward becomes a mechanical pass over a controller that's already thin.

**New services are named after the aggregate/entity they own, matching existing precedent** (`LotService`, `ProductPassportService`, `IgnoredLotService`, `ClientErrorService`) rather than one large `EbayApplicationService` facade. `LotForSaleService` already exists for the unrelated `LotForSale` aggregate, so `LotService` (for `Lot`) doesn't collide. `ClientErrorService` is a one-method wrapper around a two-line body - added anyway for consistency with the architecture rule and because `AGENTS.md`'s own review checklist makes no exception for "the logic is trivial."

**Publish-only port, not the `IMeasurementWatchedOnEbayPublisher` publish-and-save pattern.** That existing publisher calls `SaveChangesAsync` itself because it's invoked standalone with nothing else to persist. Here, `LotService.UpsertLotInfoAsync` needs to publish `CalculatePricesForLot` in the *middle* of an operation that also writes the `Lot` aggregate and removes an `IgnoredLot` row - all of which must commit together in one final `SaveChangesAsync`/transaction. A port that saved on every publish would either double-commit or require the service to fight the port's own transaction boundary. Decision: `IPriceRecalculationPublisher` (name tentative - finalize during implementation) with `PublishForLotAsync`/`PublishForProductAsync`/`PublishForAllAsync`, each just calling `IPublishEndpoint.Publish` and returning - no `SaveChangesAsync` inside. The calling service's own unit-of-work commit flushes the outbox message together with everything else, same as today's `_publishEndpoint.Publish(...)` call sequenced before `_writeModelUnitOfWork.SaveChangesAsync(...)`.

**`CalculatePricesForProductAsync`/`CalculatePricesForAllAsync` move onto existing/new services rather than becoming their own tiny use-case type per method.** `CalculatePricesForProductAsync` is Product-scoped, so it becomes a method on the already-existing `ProductService`. `CalculatePricesForAllAsync` isn't scoped to any one aggregate; add it to the new `LotService` (the thing being recalculated is lot pricing) rather than inventing a service whose only job is one fire-and-forget trigger - alternatives (a dedicated `PriceRecalculationService`, or leaving it as a direct `IPriceRecalculationPublisher` call from the controller) were considered and rejected: a whole service for one trigger is over-engineering for this codebase's stated KISS preference, and calling the publisher port directly from the controller would reintroduce exactly the layering violation this change exists to remove.

**Contract merge target style: `WebApi.yaml`'s (abstract controller + `ActionResult<T>`), not the legacy style.** `AGENTS.md`'s "Code generation" section already says not to add new endpoints to the legacy contract, so the new style is the stated direction; picking the legacy style instead would mean re-migrating `WebApiController.cs`'s already-correct endpoints backward. Every legacy endpoint's `throw NonOkHttpAnswerException.X()` call becomes a `return NotFound()`/`return BadRequest(...)`-style `ActionResult`, done endpoint by endpoint so each one stays independently testable against `Tests.Integration`'s existing status-code assertions.

**Merge the YAML documents by moving each legacy path into `WebApi.yaml` one at a time (or in small batches), not a single mechanical file concatenation.** A straight concatenation would still need per-path adjustment for operationId/schema-naming collisions and the generation-style difference; doing it endpoint-by-endpoint means each step has a small, independently verifiable diff (regenerate, `dotnet build`, run the integration tests covering that endpoint) instead of one large all-or-nothing regeneration.

## Risks / Trade-offs

- **[Risk] The contract/generation-style merge accidentally changes an error response's shape** (e.g. a legacy `NonOkHttpAnswerException`'s problem-details body vs. the new style's `ActionResult` default body) for an endpoint some client (Chrome extension, Frontend) parses structurally, not just by status code. → **Mitigation**: before merging each endpoint, check `Server.Client`/`ChromeExtension`/`Frontend` for any code that reads the error response body (not just the status code) for that specific endpoint; where found, verify the new shape matches or adjust the generation config so it does, before moving on to the next endpoint.
- **[Risk] Moving `UpsertLotInfoAsync`'s domain orchestration into `LotService` while its manual input-shape validation stays in the controller could let the two drift out of sync** (e.g. someone adds a new required field to `LotInfo` and updates the service but forgets the controller-side check, or vice versa). → **Mitigation**: keep the validation block immediately preceding the `LotService` call in the controller, with a short comment pointing at this design decision, so the two stay visually adjacent even though they're in different files.
- **[Trade-off] This is a larger diff than a typical single-concern PR** (up to 4 new services, a new port, ~700 lines of controller rewritten, then every endpoint's contract touched). → Accepted: broken into small, independently-buildable-and-testable tasks below, each verified against the full existing test suite before moving to the next, matching how `complete-hexagonal-migration` was executed task-by-task.

## Migration Plan

No data migration, no deployment-order dependency, no rollback concern beyond normal git revert - this changes only C#/YAML source and generated code, not runtime schema or persisted data shape. Steps (detailed in tasks.md):

1. Add the four new `Server.Application.New` services and the publish-only port/adapter, one at a time, each ending with the controller calling the new service instead of the repositories/unit-of-work/publish-endpoint it used before, verified against `dotnet build` + `Tests.Unit` + `Tests.Integration` after each.
2. Remove the `MassTransit` `PackageReference` from `Server.Adapters.Driving.WebApi.csproj` once step 1 leaves nothing in that project referencing it.
3. Merge the OpenAPI contract endpoint-by-endpoint (or in small logically-grouped batches) from `Legacy/Ebay.yaml` into `WebApi.yaml`, regenerating and adjusting each affected controller method's implementation to the new style, verified the same way after each batch.
4. Delete `Legacy/Ebay.yaml`, the legacy NSwag targets, and the `Server.Controllers.Generated` namespace once nothing references it.
5. Update `src/Ebay/AGENTS.md`'s "Code generation" section.
