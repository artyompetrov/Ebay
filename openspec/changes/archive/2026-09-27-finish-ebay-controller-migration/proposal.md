## Why

`complete-hexagonal-migration` (archived) moved `EbayController`/`EbayControllerImplementation` out of the legacy `Server.Application` project, but did not finish migrating it to the target architecture. Reviewed in PR #355, the repo owner flagged that the controller still holds real orchestration logic instead of being a thin HTTP-to-application adapter: it injects `IPublishEndpoint` (MassTransit), `IWriteModelUnitOfWork`, and 8 repositories directly, and for Lot/ProductPassport/IgnoredLot/ClientError/Currency/SaleAdvertisement-history operations it *is* the use-case layer (loads aggregates, calls `SaveChangesAsync`/`BeginTransactionAsync`, publishes messages) rather than delegating to one, unlike `_measurementService`/`_matchedMeasurementService`/`_tubeWorkingPointService`/`_productService`, which already follow the correct shape. The end state must be a correct hexagonal schema with no business/orchestration logic in the adapter: `Server.Adapters.Driving.WebApi` maps HTTP to application calls and back, nothing else. The controller's direct `MassTransit` package reference is a visible symptom of the same gap - a driving adapter should not need a driven-adapter-ish messaging library at all.

Separately, the OpenAPI contract is still split across `Server.Contracts/Legacy/Ebay.yaml` and `Server.Contracts/WebApi/WebApi.yaml`, a separation that existed only to keep the legacy contract (once owned by the now-deleted `Server.Application`) isolated from the new one during the migration. Both YAMLs now live in and are consumed by the same project, so the split is vestigial and should be closed out once the controller itself no longer has two different implementation styles to bridge.

## What Changes

- Add `Server.Application.New` use-case services for the concerns `EbayControllerImplementation` still orchestrates directly: Lot (aggregate lifecycle plus its purchase history), ProductPassport (including its ordering logic), IgnoredLot, and ClientError. Each follows the existing pattern already used by `MeasurementService`/`ProductService`/`TubeWorkingPointService`: repository port + domain method + `IWriteModelUnitOfWork`, with `Server.Application.New` still depending on nothing under `Server.Adapters.*`. (Currency and SaleAdvertisement/ProductEmailSendHistory turned out, on closer inspection, to already be read-only in this controller via proper query ports (`ICurrencyQueries`, `IProductEmailSendHistoryQueries`) - no write path for either exists here, so neither needs a new service.)
- Where a use-case needs to publish a MassTransit message (`CalculatePricesForLot`/`CalculatePricesForProductRequested`/`CalculatePricesForAll`), add a narrow publish-only port in `Server.Application.Abstractions.Driven`, implemented in `Server.Adapters.Driving.MassTransit` (matching the existing `IMeasurementWatchedOnEbayPublisher` precedent for the port-in-abstractions/impl-in-adapter split, but publish-only - unlike that publisher, these calls sit inside a larger unit of work with other repository changes to persist in the same `SaveChangesAsync`, so the port must not call `SaveChangesAsync` itself). `Server.Application.New` and the controller never reference `IPublishEndpoint`/MassTransit directly.
- Rewrite `EbayControllerImplementation`'s affected methods to call the new services instead of repositories/`IWriteModelUnitOfWork`/`IPublishEndpoint` directly. When finished, the controller has zero direct repository, unit-of-work, or MassTransit dependencies - only application-layer service/query-port dependencies and HTTP<->DTO mapping.
- Remove the now-unneeded `MassTransit` `PackageReference` from `Server.Adapters.Driving.WebApi.csproj` once nothing in that project references it directly.
- **BREAKING (internal only)**: merge `Server.Contracts/Legacy/Ebay.yaml` into `Server.Contracts/WebApi/WebApi.yaml` as one OpenAPI document, generated with the newer style (abstract controller + `ActionResult<T>`) rather than the legacy style (concrete `Controller` base class + thrown `NonOkHttpAnswerException`). Every legacy endpoint's generated shape changes as a result, though the HTTP contract observed by API clients (paths, methods, request/response bodies, status codes) does not.
- Delete the now-unused `Legacy/Ebay.yaml`, the `GenerateLegacyApiClients`/`IncludeGeneratedControllers`-legacy-half NSwag targets, and the `Server.Controllers.Generated` namespace's generated types once nothing references them.
- Update `src/Ebay/AGENTS.md`'s "Code generation" section to drop the Legacy/WebApi contract distinction once there is only one contract.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

None - this is an internal refactor of how existing, already-shipped endpoints are implemented (moving logic from the driving adapter into the application layer, and unifying two code-generation styles into one). No endpoint's path, request/response shape, status codes, or observable behavior changes. `skip_specs: true` is set in `.openspec.yaml` accordingly.

## Impact

- **Code**: `Server.Adapters.Driving.WebApi/Controllers/EbayControllerImplementation.cs` (rewritten, not just trimmed), `Server.Application.New` (new services), `Server.Application.Abstractions.Driven`/`.Driving` (new ports, if any), `Server.Adapters.Driving.MassTransit` (new publisher(s), if any), `Server.Contracts/Legacy/Ebay.yaml` (deleted), `Server.Contracts/WebApi/WebApi.yaml` (grows to cover every endpoint), `Server.Adapters.Driving.WebApi.csproj` (NSwag targets simplified, `MassTransit` reference removed), `Server.Client` (generated client regenerates from the merged contract - consumers of the generated `EbayClient`/`WebApiClient` types may need to adjust to the unified generated shape, though the Chrome extension and Frontend only call it through the typed client, not the generated types directly).
- **Tests**: existing `Tests.Integration` flows exercising these endpoints (`LotPricingFlowTests`, `IgnoredLotFlowTests`, others) must keep passing unchanged, since they assert on HTTP behavior, not generated-code shape - they are the main safety net proving the contract merge and service extraction didn't change behavior.
- **No production data/migration impact**: no database schema, table, or DI-registration-visible-to-ops changes are implied by this change (unlike `complete-hexagonal-migration`, which had a real Identity-cutover risk).
