## 6. Merge the OpenAPI contract into WebApi.yaml

For each group below: move its paths/schemas from `Legacy/Ebay.yaml` into `WebApi/WebApi.yaml`, regenerate (`dotnet build`), and update the corresponding `EbayControllerImplementation` method(s) to the new abstract-controller/`ActionResult<T>` style (matching `WebApiController.cs`'s existing pattern), replacing each `throw NonOkHttpAnswerException.X()` with the equivalent `ActionResult` (checking design.md's risk note about response-body shape for any endpoint a client parses structurally, not just by status code, before moving on).

**Reordering note:** tasks 6.1-6.7 and 7.1 were executed together in one pass instead of endpoint-group-by-group, because NSwag's abstract-controller generation and the app's route table are both all-or-nothing per contract document: as soon as the merged `WebApi.yaml` contains a path also served by the still-generated legacy `EbayController`, ASP.NET Core throws `AmbiguousMatchException` at request time for that route. There is no way to keep the legacy controller alive for not-yet-ported groups while routing already-ported groups through the new merged controller from the same merged document. So the legacy contract/generation path (7.1) was removed at the same time as the full 39-method port into `WebApiController.cs`, and verified as one unit (full `dotnet test` pass) rather than per group.

**Error-response-shape decision (supersedes the "replace `throw NonOkHttpAnswerException.X()` with the equivalent `ActionResult`" line above):** `NonOkHttpAnswerException`/`ErrorFilter` stayed as-is and are still thrown from `WebApiController`'s ported methods. `ErrorFilter` is registered globally (`AddControllers(options => options.Filters.Add<ErrorFilter>())`), so it applies uniformly to the merged controller with zero behavior change - mapping HTTP status/error-body shape is a driving-adapter (HTTP) concern, not business logic, so keeping it doesn't conflict with the "no business logic in the adapter" goal. This fully preserves response shapes (status codes, e.g. `NotFound400()`'s HTTP 400 for not-found, and `ValidationProblemDetailedInfo` bodies) for every consumer, including `Frontend/Extensions/ModelExtensions.cs`'s `FillValidationMessageStore` (product create/update forms) and `Measurements.razor`'s `GetTubeWorkingPointAsync` `StatusCode == 400` check - both confirmed by reading the client code before merging, per design.md's risk note.
